# 事件日志保护规则与下一阶段任务（2026-09-19）

## 0. 复盘：为什么会丢

08 冻结窗口第一区段（09-14 04:04 → 09-15 08:39，1,032 观测 / 29 笔成交）**唯一一份事件文件**位于本地 `results/short-duration-digital-fair-value/server-low-latency-008-5m-30s/events.ndjson`。写入端本身是**只追加**（`EventJournal::open` 用 `OpenOptions::new().create(true).append(true)`），丢失发生在同步环节：

```bash
rsync -azP --itemize-changes aws-eu:/home/ubuntu/poly/results/ results/
```

服务器上该同名路径当时只有第二区段（其目录 09-18 09:35:51 才创建），rsync 以"源端覆盖同名"的语义把本地 76.8 MB 的第一区段替换成了 43.2 MB 的第二区段。rsync 没有 `--delete`（不是删除），也没有"保留更完整副本"的概念。

**结论：事故原因是"同名路径 + 无保护的下载同步"，不是策略写入端。**

## 1. 防复发措施

### 1.1 脚本层（本次已实现，可直接用）

| 脚本 | 作用 |
|---|---|
| `scripts/archive_event_journal.sh status <journal>` | 打印 journal 的 size / sha256 / `run_started` 数 / 首末事件时间 / 已归档段数 |
| `scripts/archive_event_journal.sh archive <journal> <label>` | 把当前文件**复制**为 `archive/<stem>-<UTC时间>-<label>.ndjson`，校验 sha256 一致后写入 `archive/index.ndjson`；同名不覆盖 |
| `scripts/sync_results_down.sh dry-run [scope]` | 只预览 rsync 变更，**不写任何东西**；`>f+++++++++` 表示目的端不存在，`>f.st......` 表示**将覆盖既有文件** |
| `scripts/sync_results_down.sh fetch [scope]` | 把远端结果落到 `results-incoming/<UTC时间戳>/`，**live 目录不动** |
| `scripts/sync_results_down.sh merge [staged]` | 逐个文件判定：新增→复制；内容相同→跳过；**本地是远端的严格前缀（追加型）→更新并保留 `.bak-<时间>`**；**已分叉→保留本地并告警**，绝不静默覆盖 |

本次已在 008 上跑过一遍完整流程（结果留档）：

```

merge                       updated events.ndjson + system.log（本地是严格前缀，旧版存为 .bak-20260919T031320Z）
archive(server-aws-eu)      47,160,979 B  sha256 d99fd9ae…  events=35,261  last=2026-09-19T03:10:07Z
```

### 1.2 流程层（必须固化的习惯）

1. **一个批量只在一台机器上跑**；跨机器混跑会让同一窗口的执行环境（延迟、网络、REST 回退）不一致，冻结窗口的结论也无法解释。
2. **每段结束立刻归档**：`archive_event_journal.sh archive <journal> <host>`。归档用不同文件名，因此**天然免疫同名覆盖**。
3. **禁止把 `results/`、`logs/` 从服务器直接同步进 live 目录**。只用 `fetch`（落到 `results-incoming/`）+ `merge`（安全判定）。
4. **下拉前先 `dry-run`**，只要看到 `>f.st` / `>fcst`（覆盖既有文件）就先停下来问"本地这份是否更完整/更旧"。
5. **不要用 `-u` 代替保护**：旧段文件的 mtime 更旧，`-u` 照样会被覆盖。
6. **清理服务器目录前先归档**（服务器 history 里 `rm -rf short-duration-digital-fair-value` 这类命令要改为"先 fetch 归档，再删"）。
7. **启动时留痕**：每次 `start` 把 `run_started` 数、首末事件时间、文件大小、sha256 追加到 `logs/<batch>/launch-history.ndjson`（跨重启可审计）。

### 1.3 监控层

1. **存活监控**：每 15 分钟查 `status`（观测/成交/结算计数单调递增、`last` 时间推进）；10 分钟无新增即告警并重启（同二进制）。
2. **归档覆盖检查**：在每次正规分析前跑一次 `archive_event_journal.sh status`，确认"已有归档段的 sha256 覆盖当前文件的前缀"。
3. **磁盘/保留策略**：`results/` 长期保留（`results-incoming/` 可定期清理，`archive/` 不清理）。

### 4.2 为什么是这个顺序

```
P0（安全流程）      → 让证据"不会消失、不会串味"（证据有效性前提；008 事故的反面教材）
  ↓
P1-1（正确基准）    → 没有正确的尺子，后面所有结论都不可信
  ↓
P1-2（换 σ）        → 唯一还没试过、且有可能翻盘模型质量的改动
  ↓
P1-3（切片）        → 若 P1-2 有效，确定它体现在哪一段价格/信息量上
  ↓
P2（前瞻判定）      → 一次性、预注册、不可回头调参的最终判定
  ↓
P3（合并/放弃 + 退路）
```

P0 与其他任务的关系是**元层面**的：它不验证策略，只保证"前瞻判定的证据不会像 008 那样变得不可用"。没有它，P2 的结论随时可能被一次误同步作废。

### 4.3 明确不验证什么

- **不验证"能不能赚钱"**。整组任务按**证伪优先**设计：每个任务都能给出"此路不通"的二值结论，且预期是先验偏负面的（卖价基准全面落后、逐份 ex-post 只有声称值的 -11%）。
- **不验证执行层假设**（排队、部分成交、真实撤补单）——回测与 shadow 都不含这些；只有在 P2 通过后才谈最小额度实盘复核。
- **不验证"市场完全没有机会"**——只验证"这条**方向性概率定价**的腿有没有优势"。
