# Binary Complement Arbitrage 全量本地回测分析（2026-08-31）

## 结论

本地历史数据证明 YES+NO 同快照低于 1 的理论价差确实存在，但没有证明它能被当前普通公网 REST 执行链路捕获。只在零预检、零第二腿延迟的理想模型中有较多正收益成交；加入 50–250 ms 预检延迟后，双腿成交几乎完全消失。

结合服务器 dry-run 中平均约 161 ms 的 REST 请求延迟，以及 40 个手续费后为正的实时信号经 REST 复核后双腿成交为 0，当前双 taker 版本不应进入真实资金运行，也不应通过降低深度或收益门槛强行增加成交。

## 本次修改

- 回测报告新增实际市场数、有效/空市场数、总快照数、双边报价覆盖、双边完整盘口覆盖、资产分布、起止时间以及 offset/limit。
- 当 `BACKTEST_MARKET_OFFSET` 与 `BACKTEST_MAX_MARKETS` 选择不到市场时直接报错，避免再次生成看似有效但实际只覆盖极少市场的报告。
- 新增策略专属的 `BINARY_COMPLEMENT_ARBITRAGE_BACKTEST_FEE_RATE` 与 `BINARY_COMPLEMENT_ARBITRAGE_BACKTEST_FEE_EXPONENT`，当前设为 `0.07/1`；不再借用其他策略的全局回测手续费假设。
- 当前源码已经支持将 `yes_price_too_low`、`no_price_too_low`、`near_market_end` 等准入拒绝候选标记为 `source=admission_rejected`，并执行完整的 0/25/50/100/250/500 ms REST Shadow。服务器需要部署新编译的二进制后才会产生这些记录。

## 两种手续费假设

为了避免本地默认手续费和服务器实际费率不同造成偏差，本次运行了两轮相同覆盖范围的回测：

1. 历史默认假设：`fee_rate=0.25`、`fee_exponent=2`。
2. 服务器当前市场观测：`fee_rate=0.07`、`fee_exponent=1`。

两轮的可执行性结论一致。第二种费率在极端价格附近不一定更低，因此零延迟成交由 615 次下降到 444 次，理论净收益由 111.242468 USDC 降至 89.175599 USDC。

## 关键场景结果

以下以服务器当前费率假设 `0.07/1` 为主：

| 场景 | 双腿成交 | 单腿/退出 | 净收益 |
|---|---:|---:|---:|
| 100 ms 确认，0 ms 预检，0 ms 第二腿 | 444 | 0 | +89.175599 USDC |
| 100 ms 确认，0 ms 预检，250 ms 第二腿 | 278 | 166 | +33.311640 USDC |
| 100 ms 确认，50 ms 预检，250 ms 第二腿 | 0 | 2 | -0.663422 USDC |
| 100 ms 确认，100 ms 预检，250 ms 第二腿 | 0 | 2 | -0.663422 USDC |
| 基准：100 ms 确认，250 ms 预检，250 ms 第二腿 | 0 | 1 | -0.552112 USDC |
| 100 ms 确认，250 ms 预检，0 ms 第二腿 | 1 | 0 | +0.108796 USDC |

零预检、250 ms 第二腿场景虽显示总 PnL 为正，但第二腿失败率为 37.39%（166 / 444），其中 165 次依赖紧急退出，不能视为低风险套利。历史离散快照也无法证明紧急退出能取得模拟价格。

在所有预检延迟大于 0 的 23 个敏感性场景中，只有“250 ms 预检、0 ms 第二腿”出现 1 次双腿成交；其余有实际执行事件的场景以单腿后亏损退出为主。真实系统不可能保证第二腿延迟为 0，因此这 1 次不能作为可交易证据。

## 基准漏斗

当前费率假设下，基准场景共有 210,148 次表面候选、5,796 次通过连续确认，但最终双腿成交为 0。主要拒绝原因：

| 原因 | 次数 |
|---|---:|
| 信号仍在连续确认阶段 | 158,094 |
| 信号深度低于 2 USDC | 46,258 |
| UP/YES 执行深度不足 | 5,277 |
| DOWN/NO 执行深度不足 | 373 |
| 手续费后净边际不足 | 113 |
| 最小腿金额不足 | 19 |
| 第二腿覆盖不足 | 13 |

BTC、ETH、SOL 在基准场景中均为 0 次双腿成交；唯一执行事件发生在 SOL，并以紧急退出亏损 0.552112 USDC 结束。

## 如何理解回测报告的 readiness

自动报告给出 `READY_FOR_PAPER_DRY_RUN_LATENCY_CALIBRATION`，含义只是“零延迟研究场景存在足量理论成交，应该用 PAPER 测真实延迟”，不等于策略可以实盘。

本项目已经完成这一步 PAPER 校准，而实时结果是：40 个手续费后为正的 WebSocket 信号中，REST 双腿可成交为 0。因此结合两个阶段后的最终判断应为：

- 理论关系存在；
- 普通公网 taker-taker 执行不可行；
- 当前不满足真实资金运行条件。

## 下一步

1. 将本次 release 二进制部署到服务器，继续 PAPER，重点收集 `source=admission_rejected` 的低价侧和临近结束候选。
2. 不调整 `MIN_ASK_DEPTH_USDC=2.0`、动态手续费门槛或最小净收益门槛。
3. 收集至少 100 个被准入规则拒绝但手续费后为正的独立候选；若 REST 最快组双腿可成交仍为 0，停止当前双 taker 路线。
4. 若继续研究，应转向原子化/并发执行能力或 maker-maker、maker+taker 结构；这些属于新执行模型，必须单独回测和 dry-run。
