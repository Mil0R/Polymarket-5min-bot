# Polypulse 第二阶段优化结果与后续任务

> 延续依据：`docs/CODEBASE_ANALYSIS.zh-CN.md` 第 10 节，以及第一阶段实施结果  
> 实施日期：2026-08-13

## 1. 本阶段结论

本阶段继续完善了真实交易前的安全闸门、订单后续成交同步、崩溃恢复审计和演练能力。交易链路新增以下约束：

```text
YES/NO 行情配对
  → 校验快照年龄和两腿时间偏差
  → 相同市场/价格信号去重
  → 查询两腿当前 tick size
  → 买入限价向上对齐 tick
  → 最终盈利与风险额度复核
  → Dry-run 模拟，或实盘提交
  → 用户 WebSocket 累计成交增量同步
  → 状态日志持久化
  → 恢复卖单累计成交查询与结束判定
```

第一阶段解决了“是否应当交易”和“即时响应如何记账”；本阶段重点解决“行情是否仍然可信”“订单提交后又成交怎么办”“进程重启后如何识别未完成风险”三个问题。

## 2. 已完成优化

### 2.1 Dry-run 演练模式

新增 `DRY_RUN`，启用后：

- 仍连接真实市场数据、认证只读接口和用户订单流；
- 仍执行行情过滤、tick size 查询、最终报价、风险预留、仪表盘和本地状态日志；
- 双腿订单按完全成交进行本地模拟；
- 不提交订单、不撤单、不执行 Merge、不执行收尾卖出，也不运行仓位平衡写操作。

这使配置、行情、机会判定和本地风控可以在不修改账户状态的前提下联调。Dry-run 不是离线回测：它仍依赖网络、有效认证和实时数据。

### 2.2 行情新鲜度与两腿一致性

新增：

- `BINARY_COMPLEMENT_ARBITRAGE_MAX_BOOK_AGE_MS`：任一腿快照允许的最大年龄，默认 2000ms；
- `BINARY_COMPLEMENT_ARBITRAGE_MAX_BOOK_SKEW_MS`：YES/NO 时间戳最大偏差，默认 1000ms；
- 对明显位于未来的异常时间戳拒绝交易。

订单簿监控仍允许任一腿先更新并复用另一腿缓存，但只有通过年龄和偏差检查的组合才进入套利检测。

### 2.3 信号去重

新增 `BINARY_COMPLEMENT_ARBITRAGE_SIGNAL_COOLDOWN_MS`，默认 3000ms。相同 condition、相同 YES/NO 最优价在冷却期内只准入一次；价格变化可立即形成新信号。

它与账户级最短交易间隔职责不同：信号去重减少同一行情重复排队，最短交易间隔继续限制实际下单频率。

### 2.4 tick size 感知报价

最终报价会并行查询两腿当前市场 tick size，并采用对买单保守的向上对齐：

```text
buy_limit = ceil(raw_limit / tick) × tick
```

对齐后的价格再次参与盈利校验和名义金额换算，避免 SDK 在构建订单时才因价格精度拒单，也避免向下舍入造成“校验价和真实限价不一致”。tick size 每次报价实时查询，没有永久缓存，因其可能随市场状态变化。

### 2.5 用户订单 WebSocket 与累计成交同步

启用 SDK 的认证 WebSocket 能力，每个窗口订阅相关 condition 的订单事件。`RiskManager` 建立本进程订单 ID 到订单对的映射，并按 `size_matched` 累计值计算增量：

- 只处理本进程拥有的订单 ID；
- 仅将新增成交量写入仓位和敞口，避免重复事件重复记账；
- 每次有效增量后重新分类双腿完成、部分成交或单腿成交状态；
- 用户流中断时退出当前订阅循环并重建窗口流。

这补上了 HTTP `post_order` 即时响应与订单稍后成为 maker 成交之间的状态空档。

### 2.6 追加式状态日志与启动保护

新增 `STATE_JOURNAL_FILE`，默认 `order-state.ndjson`。每条记录包含：

- 时间、pair ID、condition ID；
- YES/NO 已成交数量；
- `both_filled`、`partially_filled`、`one_sided`、`recovering`、`recovered` 等状态；
- 状态变化原因。

每次追加后执行 flush 和数据同步。启动时重放每个 pair 的最后状态；若存在未完成状态，默认拒绝继续实盘运行，避免重启后在未知单腿风险上继续开仓。Dry-run 没有账户写操作，因此允许启动但会输出警告，便于排查。

`ALLOW_UNRESOLVED_STATE=true` 只提供人工核对后的显式放行，不会自动把旧状态判为已恢复。

### 2.7 恢复卖单生命周期完善

HedgeMonitor 现在不只防止重复卖单，还会对已提交的恢复 GTC 卖单：

- 查询 CLOB 订单的累计 `size_matched`；
- 只按新增成交量减少仓位和敞口；
- 完全成交后移除监控并写入 `recovered`；
- 撤单后清除活动订单标记，允许后续行情再次触发退出；
- 查询失败时保留原状态，不盲目重挂；
- 若缺失腿后续成交已经覆盖不平衡，不等待止盈/止损，直接结束恢复监控。

同时修正部分卖出记账顺序：先按卖出前仓位比例扣减成本，再减少 share 数量，避免卖出一部分却错误清空全部成本。

### 2.8 风险预留泄漏修复

复查发现，下单前成功预留风险额度后，如果随后因本地仓位严重失衡或全局交易冷却而跳过，原路径没有释放 reservation。该问题会造成进程内敞口虚高并逐步停止交易。

现在两个跳过路径都会先释放 reservation；执行成功和失败路径仍分别释放。新增测试覆盖部分卖出后的剩余成本比例。

### 2.9 配置与运行安全

- 布尔配置统一严格接受 `true/false`、`1/0`、`yes/no`、`on/off`，非法值阻止启动；
- Wind-down 与定时 Merge 一样，在实盘启用时要求完整 Builder 凭证；
- `.env.example` 和中英文 README 已补充 Dry-run、行情时效、信号去重和状态日志说明；
- 本地运行生成的状态日志和机会日志已加入 `.gitignore`。

## 3. 测试与检查

自动测试新增覆盖：

- 过期、偏斜和未来行情时间戳；
- 相同信号冷却与价格变化准入；
- 状态日志重放和终态过滤；
- 严格布尔配置；
- 订单对累计成交状态分类；
- 非 0.01 tick 的买价对齐；
- 部分卖出后成本按比例保留。

本阶段使用以下命令验证：

```bash
cargo fmt --all -- --check
cargo check --all-targets
cargo test --all-targets
cargo clippy --all-targets
git diff --check
```

测试不连接真实账户执行订单、Relayer 或 Polygon 写交易。

## 4. 仍需优化、完善和补充的任务

以下按优先级排列。

### P0：实盘前必须完成

1. **真实 Paper soak test**：至少连续运行多个市场窗口，验证用户流重连、行情时间戳单位、tick size 变化、Dry-run 日志增长和窗口切换；当前自动测试没有网络集成环境。
2. **状态日志与真实账户自动对账**：当前未解决状态会阻止启动，但仍需人工核对。应在启动阶段查询订单、成交和 Data API/链上持仓，生成明确的 reconcile 结果后再决定继续。
3. **恢复单重启接管**：状态日志记录恢复状态，但尚未持久化足够的 token、订单 ID、原始数量和已记账成交量来自动重建 HedgeMonitor。
4. **WebSocket 断线策略**：目前断线会重建窗口订阅；应增加指数退避、连接健康指标、断线期间禁止新开仓，以及恢复后订单/成交补拉。
5. **订单状态语义实测**：在真实小额环境确认不同订单类型下 `taking_amount`、`size_matched`、取消响应和用户流事件顺序，并固化为适配层测试样例。

### P1：高价值工程完善

6. **主循环进一步拆分**：将 `main.rs` 中窗口会话、用户流、行情策略、wind-down 和定时任务抽为服务，降低单函数复杂度和状态交叉。
7. **Relayer 参数对象化**：多个链上/Relayer 函数仍有 8–11 个参数，Clippy 的 `too_many_arguments` 提示反映了真实可维护性问题。建议引入认证上下文、钱包上下文和交易请求结构体。
8. **统一仓位变更 API**：把“成本扣减 + share 变更”封装为单个原子语义方法，避免调用顺序再次出错；为 Merge、恢复卖出和 wind-down 共用。
9. **恢复单事件统一**：当前套利买单由用户 WebSocket 同步，恢复卖单由 HTTP 查询同步。应建立统一的 owned-order registry，由同一事件处理器处理买卖方向和用途。
10. **结构化指标**：增加行情拒绝原因、报价拒绝原因、WebSocket 重连、订单延迟、撤单失败、恢复时长和 journal unresolved 数量等指标。
11. **日志轮转与保留**：NDJSON 目前只追加，应增加按日期/大小轮转、归档和完整性检查，防止长期运行占满磁盘。

### P2：功能扩展与质量体系

12. **历史回放/离线 Paper 引擎**：将策略判断从实时 I/O 抽离，用记录的订单簿和订单事件做确定性回放。
13. **故障注入测试**：覆盖第一腿成功第二腿超时、取消失败、用户流重复/乱序、恢复单部分成交、进程在 journal 写入前后崩溃等场景。
14. **集成测试沙箱**：为 CLOB、Gamma、Data API 和 Relayer 建立 mock server/录制响应，避免只依赖纯逻辑单元测试。
15. **自动 Redeem 队列**：仅在具备 condition resolution 确认、链上 finalization 检查、condition 级幂等状态和失败重试后接入；不应直接塞入实时行情主循环。
16. **成本模型升级**：Data API 同步仍按每 share 1 美元保守计入敞口。可结合成交历史维护真实加权成本，同时保留保守风险上限视图。
17. **CI 质量门禁**：加入 fmt、check、test、依赖审计和 Clippy。当前 `cargo clippy --all-targets` 可运行，但 `-D warnings` 仍会被既有长参数函数阻止，应在第 7 项重构后升级为零警告门禁。
18. **安全与运维文档**：补充私钥最小权限、密钥轮换、日志脱敏、状态日志备份、紧急停机和人工对账 runbook。

## 5. 建议的下一轮顺序

建议下一轮按以下顺序执行：

```text
连续 Dry-run soak test
  → 启动自动对账与断线禁开仓
  → 恢复单持久化和重启接管
  → 统一 owned-order 事件模型
  → 主循环/Relayer 参数对象化
  → mock 集成测试与故障注入
  → CI 零警告门禁
```

在前三项完成前，不建议仅因为单元测试通过就直接提高实盘订单金额。
