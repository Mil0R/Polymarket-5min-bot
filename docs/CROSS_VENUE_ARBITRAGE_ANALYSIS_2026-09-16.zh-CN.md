## 3. 为什么没有机会或交易

### 3.1 直接原因是标签未通过，不是成本参数拦截

代码先检查 ARB / ARB_FLAGGED / WATCH 标签，再检查来源场地、新鲜度和映射。最新所有记录都是 ALIGNED，因此没有进入手续费、滑点、深度、预算或净收益门槛计算。

这轮不能得出“风控过于保守”或“手续费吃掉全部利润”的结论。放宽 900 秒来源窗口、降低每份等额对冲的 0.02 USD 净收益门槛、增加预算，都不会改变本轮的标签筛选结果。

### 3.2 空配对表是下一步验证的独立障碍

即使之后出现合格标签，空配对表仍无法确定 Kalshi ticker、Polymarket slug/token、结果方向及结算规则是否等价。

现存 `inspect/report.json` 只有开始/结束事件，没有 `review_proposal`；`probe/report.json` 明确拒绝 `empty_registry`。这两份诊断报告没有验证任何真实配对。`probe` 功能已存在，但尚未获得有效输入。

### 3.3 Shadow 本身没有下单能力

该阶段目标是观察“真实盘口在费用、深度和延迟压力下是否仍有条件净收益”，并非产生实际交易。目前连这一观察所需的盘口样本也没有。

## 4. 新发现的数据质量与研究局限

### 4.1 cheaper_venue 与显示概率存在表面矛盾

最新 2,916 条重复返回中，666 条（22.84%）在“两个概率代表同一结果”的解释下，与 `cheaper_venue` 指向不一致。按来源时间戳去重后，为 408 条快照行中的 95 条；不能把重复轮询计作独立错误样本。

例如 MLB `Boston vs Texas`：Kalshi 51%、Polymarket 52%，但 `cheaper_venue=polymarket`。

返回行只有 sport、game、两个 implied_pct、gap_pp、signal 和 cheaper_venue，缺少比赛日期、明确结果身份、交易所合约 ID 和 bid/ask。可能是字段错误、结果方向差异或另有定价口径，**现有数据不能判定具体原因，更不能认定供应商造假**。应核验字段定义并与明确合约的实时盘口比对。

当前代码不会按 cheaper_venue 单独决定下单方向；审核配对后会分别计算两个对冲方向。此次所有记录也已被 ALIGNED 标签跳过，所以这一疑点不是本次零候选的直接原因，但限制了数据作为自动选市场依据的可信度。

### 4.2 价差与覆盖范围不足以推出盈利结论

显示价差的重复分布：0pp 729 条、0.5pp 431 条、1pp 1,561 条、2pp 195 条。最大只有 2pp，但它不是已核验同一结果的可执行买卖价差；不能直接解释成 2% 净收益。

本轮实际净成本应由同一结算结果的 `Poly YES ask + Kalshi NO ask`，或相反方向，按目标数量走盘口并加入手续费、滑点和失败腿风险后确定。目前这些数据缺失。

接口声明的 12 条结果每轮全部返回，是完整返回“该接口声明集合”的证据，不是全市场覆盖证据。Key 存在不等于服务端 Pro 权限已核验；报告仍为 `pro_entitlement_verified=false`、`coverage_status=unverified`，且所有 243 次 `truncated` 字段均缺失。不能把该结果外推为整个 Polymarket / Kalshi 市场没有套利。

### 4.3 前一天事件文件存在一条截断尾记录

逐文件校验发现：`events-2026-09-15.ndjson` 最后一个非空记录被截断，缺少 JSON 结尾和最终换行；最新 `events-2026-09-16.ndjson` 可正常完整解析。报告正确标记 `directory_malformed_lines=1`，并仍选择了最新运行。

仅凭本地文件无法区分运行中同步截断、写入中断或服务器源文件问题。应先核对服务器文件，再重新同步；不要直接删除或手改历史证据。

代码目前把整个目录的 malformed 计数用于稳健机会判断：目录内任一坏行都会使 `robust_conditional_pairs` 无法通过，即使坏行属于旧运行。本轮本来就没有机会，因此不改变本轮结论；但以后出现机会时会影响报告。下一批验证宜使用独立运行目录，并将“坏行所属运行及未知归属”的完整性判定列为报告改进项，不能简单忽略坏行。

## 6. 下一步优先级

1. **先核验输入可信度。** 确认 Pro 接口覆盖、字段含义、结果方向和比赛身份；向供应商核对上述 cheaper_venue 示例。不要把来源价格当作实际成交价格。
2. **准备 3–5 个明确配对。** 填入精确 ticker、slug/token、日期、规则、费用上界和审核有效期。用 `inspect` 获取规则和指纹，人工审核后才能填写 reviewed_digest。不能仅以球队名称匹配批准。
3. **运行独立 probe。** 验证规则、盘口、REST 延迟、深度、费用和两种方向；即使 PMP 全为 ALIGNED，也能完成这项诊断。区分人工选择样本与 PMP 发现样本，避免夸大扫描器能力。
4. **处理数据完整性并开启独立批次。** 核对/补同步旧尾记录，保留原始证据；新批次分开结果和系统日志。后续可改进报告的跨运行完整性归因。
5. **有有效盘口样本后再安排持续 Shadow。** 关注独立审核配对覆盖、净收益分布、延迟后存活率和不可成交原因。若长期连有效映射和可执行盘口都拿不到，优先重新评估数据源和发现方式，不继续投入交易执行开发。

当前可以保留低频采集作为辅助，但继续空配对运行 24–48 小时不是完成可行性验证的必要条件，也不能解决上述缺口。现阶段不建议降低成本保护参数、增加资金或开发实盘下单。
