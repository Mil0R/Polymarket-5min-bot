# 第九阶段优化与完善结果

## 1. 阶段目标

本阶段将双腿执行顺序从“最终价格较高的一腿优先”调整为“当前最佳卖盘更难成交的一腿优先”，并使第二腿严格跟随第一腿的确认成交量，降低顺序提交产生单腿暴露的概率。

所有验证均为本地离线验证，没有提交真实订单。

## 2. 已完成事项

### 2.1 保留两腿独立盘口深度

套利检测器此前把 YES/NO 最佳卖盘数量提前合并为共同最小值，执行器无法判断哪一腿更薄。现在 `ArbitrageOpportunity.yes_size` 与 `no_size` 分别保留各自最佳卖盘深度，最终下单数量仍取两者、每腿美元上限之间的最小值。

### 2.2 困难腿优先规则

当前排序规则为：

1. 最佳卖盘数量较小的一腿优先；
2. 两腿深度相同时，价格较低、残余资金损失较小的一腿优先。

这里的“困难度”是基于当前可可靠取得的最佳卖盘深度，不宣称等同于完整的成交概率模型。后续还可加入多档累计深度、价差、盘口年龄和历史成交延迟。

### 2.3 第一腿成交驱动第二腿

执行流程调整为：

```text
选择较薄的一腿
  → build/sign/post 第一腿
  → 对 GTC/GTD 撤销未成交余量
  → 查询累计成交，冻结第一腿数量
  → 零成交：不提交第二腿
  → 撤单失败：不提交第二腿，交给风险登记
  → 有确认成交：按成交量向下取两位小数
  → 校验第二腿最小名义金额
  → build/sign/post 第二腿
  → 撤销并核对第二腿余量
  → 将实际结果交给 RiskManager
```

FOK/FAK 的未成交余量由订单类型自身处理，不再额外依赖撤单成功。

### 2.4 失败语义收紧

- 第一腿传输失败时禁止继续提交第二腿；由于写请求结果可能不确定，仍不自动重试。
- 第一腿零成交时直接终止本次配对。
- 第一腿余量无法冻结时禁止提交第二腿，避免未知增长的第一腿与固定第二腿形成更大失衡。
- 第一腿累计成交查询失败时同样禁止提交第二腿，不使用不可靠的即时响应数量继续写入。
- 第二腿构建、签名或提交失败时返回已知第一腿成交，由现有单腿恢复监控处理。
- 风险订单注册忽略空订单 ID，避免把“未提交的一腿”登记成空键订单。

## 3. 自动化测试

新增测试覆盖：

- 套利机会保留 YES/NO 独立最佳卖盘深度；
- 最佳卖盘较薄的一腿优先；
- 深度相同时选择较低资金暴露；
- 第二腿数量只跟随第一腿确认成交量，并且不会超过计划数量。

最终验证结果：

- `cargo fmt --all -- --check`：通过；
- `cargo check --all-targets`：通过；
- `cargo clippy --all-targets -- -D warnings`：通过；
- `cargo test --all-targets`：63 个测试全部通过（库测试 7 个、主程序测试 56 个）；
- `git diff --check`：通过。

## 4. 当前边界

1. 双腿仍不具备交易所级原子性，本阶段降低但不能消除单腿风险。
2. 困难度当前只使用最佳卖盘深度；尚未使用多档累计深度、盘口价差、历史成交率和撤单延迟。
3. 第一腿 `post_order` 发生传输错误时，服务端是否已接受请求仍可能不确定；在写请求幂等或按客户端订单标识查询完成前，系统选择不发送第二腿且不自动重试。
4. 第二腿需要在第一腿撤单与累计成交查询后重新构建和签名，裸露时间可能增加；后续应通过可注入 CLOB adapter、延迟指标和隔离账户 canary 衡量实际权衡。
5. 尚未执行真实账户的部分成交、撤单竞争和 WebSocket/HTTP 事件顺序验证。

## 5. 结论

项目不再用结果价格代替成交难度，也不再无条件发送第二腿。新的顺序执行以冻结后的第一腿真实成交为上限生成第二腿，在现有非原子 CLOB 约束下显著收紧了可控的单腿风险边界。
